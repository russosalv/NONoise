Replace graphify with codebase-memory-mcp, make Regia the orchestration layer, add quick / medium / long development modes, and propose FPF validation only when it is warranted.

- **Code graph: codebase-memory-mcp replaces graphify.** The CLI installs `codebase-memory-mcp` (one native binary, no Python/uv, no LLM key) and registers its MCP server in the project for every selected tool: `.mcp.json` (Claude Code, Copilot CLI), `.vscode/mcp.json` (Copilot in VS Code), `.codex/config.toml`, `.cursor/mcp.json`, `.gemini/settings.json`. The binary is not pinned: a scaffold installs the latest release when none is on PATH and leaves an existing one alone, `--upgrade` and `--code-graph-only` move it to the latest release, and in between it is yours to update. New bundled skill `codebase-memory`; context files carry a `codebase-memory` managed block; `/index` builds the graph. `--code-graph-only` replaces `--graphify-only` (still accepted as an alias). `--upgrade` retires an unmodified graphify integration (skill, hooks, receipt) and leaves `graphify-out/` and the graphify CLI in place.
- **Regia is the orchestration layer.** For Claude Code the CLI installs the Regia mod (`regia@claude-regia`, from `russosalv/claude-regia`), which makes the main session delegate, picks model and effort per task and runs swarms of Claude, Codex and Qwen agents. The skills that did this by hand are retired: `swarm-router`, `copilot-delegate` and `gemini-delegate` are no longer shipped, and `--upgrade` removes unmodified copies. NONoise no longer installs the Codex plugin itself: Regia does, when the `codex` CLI is on the machine.
- **Development modes.** `.nonoise/sdlc-flow.md` (version 2) tags every phase with the modes it belongs to and sets `default_mode: medium`. `/polly quick|medium|long <goal>` sizes the process; with a goal and no mode Polly picks the lightest that fits. The same table ships in every context file as the `development-modes` managed block, so Codex and Copilot behave the same way. In Claude Code they map one to one onto Regia's `/regia quick|medium|long`.
- **FPF gate.** `arch-decision` now starts by deciding whether formal Haft FPF validation is warranted: an explicit request, or a costly-to-reverse decision with at least two materially different viable options. Otherwise it records a lightweight decision in the PRD frontmatter (`decision.mode: lightweight`), which `arch-sync` and `sprint-manifest` accept without the Haft runtime. FPF is never proposed in quick mode.
