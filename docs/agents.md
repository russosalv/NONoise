# Agents — the specialists NONoise installs

Since 1.9 a NONoise project carries two sets of agents: three written by NONoise, and a selection from the vendored [ECC](https://github.com/affaan-m/ECC) snapshot that follows the install profile and `--stack`. This page covers what an agent is here, where the files land, what each agent does, when the SDLC flow calls it and how to change the selection.

## Agent versus skill

| | Skill | Agent |
|---|---|---|
| **What it is** | A procedure: a `SKILL.md` the main session reads and follows | A specialist: a definition file the host runs as a subagent |
| **Who does the work** | The main session, in its own context | A separate agent with its own context and its own tools, which hands a report back |
| **Where it lives** | `.claude/skills/`, `.agents/skills/` | `.claude/agents/`, `.github/agents/`, `.codex/agents/` |
| **Typical use** | Drive a phase (`arch-brainstorm`, `sprint-manifest`, `atr`) | One bounded job inside a phase: explore, derive a blueprint, review a change |

The flow and the skills name the agent to use; the main session delegates to it and integrates the result before it reports. An agent does not own a phase and does not decide what comes next. Where the host has no agent tool, the session applies the agent's instructions itself and says that no independent review ran.

## Where they are installed

One source file per agent; the per-host files are generated by `create-nonoise` at scaffold and upgrade time (`packages/create-nonoise/src/ecc.ts`).

| Host | Agent file | Format |
|---|---|---|
| Claude Code | `.claude/agents/<name>.md` | Markdown with `name`, `description` and `tools`. The model is inherited from the session |
| GitHub Copilot | `.github/agents/<name>.agent.md` | Same body; tools mapped to Copilot's `read`, `search`, `execute` and `edit` aliases |
| Codex | `.codex/agents/<name>.toml` | `name`, `description`, `developer_instructions`. No tool list: permissions come from the parent session. The project must be trusted before Codex loads project agents |
| Cursor, Gemini CLI | none | No agent files are written for these two tools |

Every generated file starts with a provenance comment. Agents are installed in every profile except `minimal`.

## The three NONoise agents

Written by NONoise, sources in `packages/skills/_agents/`. They ship in every profile except `minimal` and do not depend on `--stack`.

| Agent | What it does | When the flow calls it | Mode |
|---|---|---|---|
| `graph-explorer` | Maps how an existing feature or area works: entry points, the call path, layers and modules, conventions in use, reusable pieces, risks and unknowns. It queries the `codebase-memory` graph first and reads source only for the symbols the graph names. Every statement carries a location, and it quotes the graph queries it ran | Before design in existing code: in `feature-design`, after `reuse-first`; in `arch-brainstorm` | medium, long |
| `blueprint-architect` | Turns an approved requirement or spec into a file-level blueprint: files to create and change, interfaces, data flow, a build sequence in which every step has a test, and a table from acceptance criteria to tests | In `feature-design`, after the exploration and before the plan is written | medium, long |
| `evidence-reviewer` | Reviews a diff against the task, spec or PRD it implements and reports only what it can prove: the exact file and line, the input or state that triggers the failure, the context it read | At the end of each implementation task, before `atr` and before a pull request, next to the installed language reviewer | medium, long |

Details that matter in practice:

- **`graph-explorer` does not design.** Its output normally becomes the "Existing behaviour" section of the spec under `docs/superpowers/specs/` (medium) or of the PRD under `docs/prd/<area>/` (long). With no graph it falls back to Glob and Grep and says the map is partial.
- **`blueprint-architect` works inside the decided architecture.** When the feature needs a choice that is costly to reverse and has more than one viable option, it stops, names the decision and the options, and leaves it to `arch-brainstorm` and `arch-decision`. Its blueprint becomes the design section of the spec (medium) or feeds the sprint breakdown (long). The plan itself is still written by `superpowers:writing-plans`.
- **`evidence-reviewer` reports proof, not patterns.** Critical and high findings need the path from an entry point to the defect, a command and its output, or a failing test; without that a finding is at most medium and worded as a question. It carries a list of the usual false positives to skip, and "No findings" is a valid result. Language- and framework-specific rules are left to the language reviewer.
- **All three are read-only.** They declare `Read`, `Grep`, `Glob` and `Bash` and are instructed never to edit files. Claude Code and Copilot receive that tool list; the Codex file has none, so there the limit is the instruction itself.
- **Quick mode calls none of them.** Quick runs no subagents.

## How they fit the SDLC flow

| Phase | Order of work |
|---|---|
| **Feature design** (medium, long) | The `reuse-first` skill records an adopt / extend / build decision → in existing code, `graph-explorer` maps the area → `blueprint-architect` derives the blueprint → the spec is closed |
| **Architecture options** (long) | `reuse-first` first, so the options build on what exists; `graph-explorer` when the area is existing code |
| **Implementation** (medium, long) | Each task closes with `evidence-reviewer` plus the language reviewer installed for the stack. A build failure goes to `build-error-resolver` or the stack's own build resolver |
| **Acceptance and sprint closure** (long) | `atr` requests `evidence-reviewer`, `pr-test-analyzer`, the language reviewer and, where the profile installed them, `security-reviewer` and `silent-failure-hunter`. The `docs-steward` skill then audits the documentation, as it does after `arch-sync` |

Only installed agents are used. Polly reads the inventory before she recommends one and never proposes an agent the project does not have. The phases are described in [`sdlc.md`](sdlc.md), the modes in [`development-modes.md`](development-modes.md).

## Changing the selection

```sh
npx create-nonoise my-app --yes --ai claude-code,copilot,codex --profile security --stack python,react
npx create-nonoise --upgrade my-app --stack python,react,go    # replaces the saved stack selection
npx create-nonoise --upgrade my-app --profile full             # changes the profile
npx create-nonoise doctor my-app                               # reports missing or modified agent files
```

- **`--stack`** takes a comma-separated list of `dotnet`, `typescript`, `angular`, `web`, `python`, `go`, `rust`, `java`, `kotlin`, `cpp`, `swift`, `php`, `ruby`, `react`, `vue`, `flutter`, `fsharp`, or `none` alone. No stack is inferred from the code.
- **`--profile`** decides the common agents (table above). `minimal` installs no agents at all, the NONoise ones included.
- **`create-nonoise --upgrade`** reuses the profile and stack saved in `nonoise.config.json`. An explicit `--stack` or `--profile` replaces the saved value: agent files no longer selected are removed when they are unmodified, and edited ones are kept and reported.

The inventory is `.nonoise/ecc/index.md`: the selected stacks, the ECC agents, the NONoise agents under their own heading, the rule files with the paths they apply to, and the ECC skills. `.nonoise/ecc/files.json` lists every file the selection owns.
